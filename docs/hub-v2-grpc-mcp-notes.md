This PR (branch `feat/hub-v2-grpc-contract`, based on `feat/hub-v2-base`) does

## Why the fields are frozen

Proto field numbers are a permanent wire contract. Step 11 of the plan lists
"renumber proto fields" under *do not*. The numbers below are chosen once,
contiguously, and must never be renumbered, reused, or repurposed. A new field
may only be **appended** with the next free number in its message. Every message
in the proto carries a comment recording its live field-number range.

## Proto ↔ `xerj-common::hub` mapping

The messages mirror the shared Rust types in
`engine/crates/xerj-common/src/hub.rs` one-to-one, so gRPC, the MCP tools and the
CLI all speak one vocabulary.

### `HubAnswer` ↔ `hub::Answer` (11 fields, 1–11)

| proto field (#)       | `Answer` field  | Rust type          | Wire form / note |
|-----------------------|-----------------|--------------------|------------------|
| `corpus` (1)          | `corpus`        | `String`           | |
| `pin_sha` (2)         | `pin_sha`       | `String`           | |
| `pin_date` (3)        | `pin_date`      | `String`           | `YYYY-MM-DD` |
| `age_days` (4)        | `age_days`      | `u32`              | proto `uint32` |
| `licence_spdx` (5)    | `licence_spdx`  | `String`           | |
| `licence_class` (6)   | `licence_class` | `LicenceClass`     | serde **kebab-case**: `adapt-with-attribution` \| `approach-only` \| `excluded` |
| `answered_from` (7)   | `answered_from` | `AnsweredFrom`     | serde **snake_case**: `local_pack` \| `hosted` \| `local_index` (NOT the `.label()` prose) |
| `mode` (8)            | `mode`          | `AnswerMode`       | serde **snake_case**: `def` \| `how` \| `files` |
| `hits` (9)            | `hits`          | `Vec<Hit>`         | `repeated HubHit` |
| `truncated` (10)      | `truncated`     | `bool`             | |
| `warnings` (11)       | `warnings`      | `Vec<String>`      | `repeated string`, one line each |

Enums carry the **serde** string form (`serde_json::to_value(..)`), not the
human-printed `AnsweredFrom::label()` ("local pack"/"hosted hub"/"local index"),
which is for the step-1 renderer only.

### `HubHit` ↔ `hub::Hit` (7 fields, 1–7)

| proto field (#)        | `Hit` field       | Rust type        | Wire form / note |
|------------------------|-------------------|------------------|------------------|
| `file` (1)             | `file`            | `String`         | |
| `line` (2)             | `line`            | `u32`            | proto `uint32`, 1-based |
| `kind` (3)             | `kind`            | `String`         | |
| `text` (4)             | `text`            | `String`         | |
| `value` (5)            | `value`           | `Option<String>` | **None ↔ ""** (see below) |
| `score` (6)            | `score`           | `f32`            | proto `float` |
| `licence_warning` (7)  | `licence_warning` | `Option<String>` | **None ↔ ""** (see below) |

**`Option<String>` ↔ proto3 `string`.** proto3 scalar strings have no presence:
a plain `string` cannot be null. The chosen contract (matching step 7's proto,
which does not mark these `optional`) is **`None` ↔ `""`**. The step-7 conversion
code maps `None → ""` on the way out and `"" → None` on the way in, for both
`value` and `licence_warning`. This is lossless in practice: a present `value`
(a const/macro literal) or a present `licence_warning` (a licence name) is never
legitimately the empty string. If a future need arises to distinguish "absent"
from "empty", add `optional` then — do not renumber.

## MCP tools to add to `xerj-mcp` `tool_specs()` (step 7, DEFERRED)

Add these three to `tool_specs()` (and the dispatch) in
`engine/crates/xerj-mcp/src/lib.rs`. They follow the existing spec shape
(`name`, `description`, `inputSchema` with `type: "object"`, `properties`,
`required`). `xerj_hub_ask`/`xerj_hub_def` return an `Answer`; the tool result
**text** is the step-1 `hub::render` output and the **structured content** is the
`Answer` JSON. `xerj_hub_find` returns the step-6 `/search` corpus grouping
(candidate corpora, not passages — it is discovery, not an `Answer`).

```json
{
  "name": "xerj_hub_find",
  "description": "Discover which hub corpora can answer a question (the step-6 /search grouping). Returns candidate corpora with their pin/licence, not passages. Local packs first, hosted second — exactly like the CLI.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "question": { "type": "string", "description": "What the agent is working on; a corpus name is never required here." },
      "k": { "type": "integer", "description": "Max candidate corpora to return (default engine value)." }
    },
    "required": ["question"]
  }
}
```

```json
{
  "name": "xerj_hub_def",
  "description": "Look up one definition in a named hub corpus: its kind, signature, and the literal value for a const/macro/define. Returns an Answer in def mode (no passages).",
  "inputSchema": {
    "type": "object",
    "properties": {
      "slug": { "type": "string", "description": "Corpus slug to resolve the symbol in." },
      "symbol": { "type": "string", "description": "Exact definition name." },
      "k": { "type": "integer", "description": "Max hits to return (default engine value)." }
    },
    "required": ["slug", "symbol"]
  }
}
```

```json
{
  "name": "xerj_hub_ask",
  "description": "Ask a hub corpus a question in one turn — no clone, no local indexing. Local packs first, hosted second. The corpus is optional (routed by the offline sketch when omitted) and is always named in the answer. Result text is the hub.rs rendering; structured content is the Answer JSON.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "question": { "type": "string", "description": "Natural-language question." },
      "corpus": { "type": "string", "description": "Optional explicit corpus slug; omit to route by sketch." },
      "mode": { "type": "string", "enum": ["def", "how", "files"], "description": "Answer shape; omit for auto." },
      "max_tokens": { "type": "integer", "description": "Soft output budget for the rendered answer." }
    },
    "required": ["question"]
  }
}
```

## The one rule both surfaces obey

**gRPC `XerjHub::ask`/`def` and MCP `xerj_hub_ask`/`xerj_hub_def` MUST call the
single `xerj_hub::ask` / `xerj_hub::def` flow that lands in step 5 — they do NOT
reimplement download / verify / restore / route.** Each surface only converts
its request into the shared params and converts the returned `hub::Answer` into
its own wire form (`HubAnswer` for gRPC, rendered text + `Answer` JSON for MCP).
`XERJ_HUB_URL` overrides the hosted base URL for both. This mirrors how the CLI
and the `xerj_code_search` MCP tool already share `xccode::run_code_query`.
