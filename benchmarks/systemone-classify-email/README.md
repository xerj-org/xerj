# Labelling documents at `autoindex` time — a local prototype for discussion #1012

[discussions/1012](https://github.com/xerj-org/xerj/discussions/1012) asks whether
`xerj autoindex` should be able to attach a best-label + score to each document while
indexing it, starting with email. Before writing any `xerj-autoindex` code, this
measures the mechanism the discussion's Q2 flagged as the local alternative to a
hosted Jev call: `POST /_decide` (`engine/crates/xerj-api/src/systemone_api.rs`), a
weighted k-nearest-neighbour vote over a labelled-history index that is **already
shipped** and sends nothing off the node.

## What this is not

- **Not a hosted-Jev measurement.** The discussion's hosted path needs the `jev-reranker`
  client extended to send classification questions instead of yes/no (its own text: "the
  current client only sends yes/no questions, it would need extending"). That extension
  does not exist, so no hosted number is claimed here — only the local `/_decide` path,
  which needed no new client code.
- **Not a real-mailbox accuracy number.** `gen_corpus.py` generates its own labelled
  emails from templates (see that file's docstring) — original text, no licence
  question, no privacy question, but also more separable than a real inbox: a real
  "personal" email sometimes has a dollar figure in it, a real newsletter sometimes asks
  a direct question. Read the number below as "does the mechanism work at all", not as a
  production accuracy estimate.

## Method

- 4 labels, matching the discussion's own example: `invoice`, `newsletter`, `personal`,
  `needs-reply`.
- 50 train + 15 held-out test emails per label (200 train / 60 test), generated by
  `gen_corpus.py`, seed 7 (deterministic — rerunning it reproduces `corpus.json` byte
  for byte). Templated text, so the 4 labels have near-exclusive vocabulary
  ("Invoice", "unsubscribe", "Hey `<name>`", "confirm by") — see the second tier below
  for why that number alone would be misleading.
- **A second, hand-authored "hard" tier** (8 emails, 2 per label): deliberately
  boundary-crossing — a personal note that mentions a dollar figure, an invoice with no
  word "invoice" anywhere in it, a newsletter that ends by asking a direct question, a
  needs-reply email phrased like a status update. Added after the first run scored a
  suspicious 100% — see [Result](#result).
- `run.py` bulk-indexes the 200 train emails into a throwaway index
  (`email-classify-proto`, `label: keyword`, `text: text`, default lexical embedder —
  no `--embed-mode neural`, no vector setup), then calls `POST /_decide` once per held-out
  email with `k=10` — the same k the published Banking77 / SMS-spam
  `decisions-as-retrieval` numbers used — and compares the returned `label` to the truth.
- `decisions.min_confidence` was left at its default (`0.0` — never abstain), so every
  test item gets a label; a real deployment would likely set this above `0.0` and leave
  low-confidence documents unlabelled instead of guessing.

## Result

Run 2026-09-22, locally built `xerj v1.0.0-rc.76`, `--insecure --port 9420`, throwaway
`--data-dir`, default lexical embedder. Raw numbers: [`results/run.json`](./results/run.json).

| Tier | n | accuracy | mean confidence | ms/item |
|---|---:|---:|---:|---:|
| held-out test (same generator as train) | 60 | **1.000** | 1.000 | 2.6 |
| hard (hand-authored, boundary-crossing) | 8 | **0.625** | 0.902 | 1.7 |

The first row is not a claim about anything — it says the templates are separable by
whatever vocabulary a template happens to use once per label, which is exactly the
failure mode this second tier exists to catch. On the hard tier, both `invoice` misses
(`P=0.000 R=0.000` on that split, `n=2`) are cases with no invoice-shaped vocabulary at
all — a casual "did the transfer land yet?" — and both were misclassified with
confidence 0.836–1.000, i.e. **wrong and confident**, not wrong and hedging. That matches
the discussion's own calibration caveat about the hosted path (ECE 0.31 on FiQA) more
than it contradicts it: this mechanism is also not calibrated to say "I don't know" on
inputs that look nothing like its labelled history — it votes on lexical/BM25 similarity
to what it has seen, and a boundary-crossing email that shares no vocabulary with its
label's training examples gets voted into whichever OTHER label it does resemble,
confidently. `decisions.min_confidence` would need to be tuned well above 0 to catch
this in practice, and even then the confidence number itself was not a reliable flag here
(0.836–1.000 covers both hits and misses in this small sample).

3 misses, all on the 8-email hard tier — full detail in `results/run.json`:

| subject | gold | predicted | confidence |
|---|---|---|---:|
| "This week at Cedarline: two quick things" | needs-reply | newsletter | 1.000 |
| "for the offsite" | invoice | needs-reply | 0.836 |
| "did that ever go through?" | invoice | personal | 1.000 |

## Reproduce

```sh
# from a built release binary (engine/target/release/xerj)
xerj -d /tmp/classify-proto-data --insecure --port 9420 &
cd benchmarks/systemone-classify-email
python3 gen_corpus.py
XERJ_URL=http://localhost:9420 python3 run.py
```

## Answering the discussion's four questions, from what this measured

1. **Emails, or something else?** Not answered by this prototype — it only shows the
   *mechanism* generalizes across a label set (nothing email-specific in `/_decide`); it
   says nothing about which document kind benefits most.
2. **Hosted vs. local-only.** The local `/_decide` path needs zero new client code and
   zero egress. It also has a cost the hosted path does not, visible in the hard-tier
   result above: it needs labelled examples *before* it can classify anything, it votes
   on similarity to what it has already seen, and it is not more calibrated than the
   hosted judge's own documented weakness — a boundary-crossing email got voted
   confidently into the wrong label here too. Whether that trade-off (no egress, no
   labelling cost saved) beats a hosted judge's own miscalibration is a product
   question this benchmark cannot settle; it can only say neither path arrives
   pre-calibrated.
3. **One best label, or a score per label?** `/_decide` already returns both — the
   winning `label` plus `confidence` (the winning label's vote share), and the raw
   per-neighbour votes are visible in its response if a caller wants to reconstruct a
   full distribution. No new work needed either way — but per the hard-tier result,
   don't read `confidence` as a trustworthy abstain signal without tuning
   `decisions.min_confidence` against a held-out set shaped like the real traffic first;
   this measurement is too small (n=8 on the hard tier) to say where that threshold
   should sit, only that 0 is not it.
4. **Where does the label live?** `label`/`text` on the record matches
   `xerj-autoindex`'s own convention (`DOC_BODY_FIELDS = ["body", "text"]` in
   `engine/crates/xerj-autoindex/src/infer/mod.rs`) closely enough that a real
   integration would likely add a plain field (e.g. `_label` / `_label_confidence`) on
   the record rather than a separate index — a separate index is what `/_decide` already
   *reads from* (the labelled history), not what it should write to.

## What would still need building

This prototype calls `/_decide` from a throwaway Python script against an
already-labelled index. Wiring it into `xerj autoindex` needs, at minimum: a CLI flag
(off by default, per the discussion's own "what I'd want to keep true"), a step in the
indexing pipeline that calls `/_decide` per document and attaches `label`/
`label_confidence` on failure-or-abstain-tolerant terms (a `/_decide` error or abstain
must not stop the run — same policy `rerank` already uses), and a decision on whether
the labelled-history index is built ahead of time by the operator or bootstrapped from a
`--label-examples` file. None of that is written yet.
